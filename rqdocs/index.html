rq query language

rq turns a Heroes of the Storm replay into a time-ordered list of typed events (deaths, ability casts, chat, pings, talents and more) and searches it with a small query language. Queries can filter on event fields, carry values from one event to the next, and relate events in time: “A then B within 45 seconds”, “A not followed by B”, “three of A within 12 seconds”, “A happened near me”.

Overview

A query is a list of statements. let names a pattern; find runs one and prints every span of the replay that matches it.

# Deathwing lands next to me, and within 45 s he dies with me among the credited players
let land = cast(hero: Deathwing, slot: D) near(me, 6)
let kill = death(victim: Deathwing, credit: me)
find land then kill within 45s

Events

Nine kinds: death, cast, key, chat, ping, talent, spawn, unitdied, levelup.

Filters

field: value pairs, ANDed. Values can be names, numbers, me/ally/enemy, wildcards, alternatives and negation.

Variables

$x binds on first use and must match the same value everywhere after, across a whole sequence.

Time

then, not followed by, preceded by, not preceded by, count >= n, all with a within window.

All times are replay time: game loops ÷ 16, shown as m:ss.f. The in-game clock agrees to within a second or two.

Quick start

# See what's in your latest game, 23:38 to 24:20, only events involving you or Epicure
MyHotsCli rq events --replay latest --from 23:38 --to 24:20 --player me,Epicure

# Run a one-line query on the latest replay
MyHotsCli rq find "find death(victim: enemy, credit: me) count >= 2 within 10s"

# Run a query file over your 50 most recent replays
MyHotsCli rq find -f chase.rq --last 50

When exploring, start with rq events to see the event lines a query would match, then write the query.

Command line

Common options

These work on rq and every subcommand.

OptionMeaning
--replay, -rReplay to read: a file path, latest, or N for the N-th newest (1 = latest). Repeatable. Default latest. Replays are found under Documents\Heroes of the Storm\Accounts\*\*-Hero-*\Replays\Multiplayer, newest by file time, across all accounts.
--last KUse the K newest replays instead of --replay. They are parsed in parallel and printed in order, newest first.
--me NAMEWho me is: a player or hero name. By default it's the player whose Battle.net id matches the …-Hero-1-<id> folder the replay sits in. Needed for replay files copied elsewhere.
--from m:ss, --to m:ssLimit events output, or find matches by their start time. Plain seconds also work (--from 90).
--no-abil-tableDon't build or load the ability slot table; casts show as Hero.#id and have no slot. Faster on a build you haven't queried before.

Replays are read with shared access, so the replay of a game the client still has open can be queried.

rq find

MyHotsCli rq find "<query>"   [common options] [--json]
MyHotsCli rq find -f file.rq   [common options] [--json]
Argument / optionMeaning
queryQuery text. Give this or --file, not both.
--file, -fRead the query from a file (conventionally .rq).
--jsonPrint results as JSON (format).

Exit code is 2 when the query doesn't parse, otherwise 0. A replay that fails to parse, or a query that can't run on a particular replay (for example it uses me but the replay has no known “me”), is reported on stderr and skipped.

rq events

MyHotsCli rq events [common options] [--kind k1,k2] [--player p1,p2]

Prints the replay header, the ten players with team and hero, then every event in time order.

OptionMeaning
--kind, -kEvent kinds to show, comma-separated or repeated. Default: all except key and unitdied, which are numerous.
--player, -pOnly events involving these players. Names or heroes (punctuation-insensitive, wildcards allowed), or me. A death involves its victim and everyone credited; other events involve their actor.

rq abil-table

MyHotsCli rq abil-table [--build N] [--rebuild] [--hero NAME]

Shows the ability slot table for a build: ability id, voted slot, share of votes, vote count, the heroes that voted and any alias name. Without --build it uses the build of --replay. --rebuild re-reads the replays even if the table is cached. --hero shows only ids that hero voted for.

Keywords (case-insensitive): let find then all not followed preceded by within near count. me, ally and enemy are keywords in value position. Event kinds and keywords can't be used as let names. Everything else is case-insensitive too: kinds, field names, let names, and name matching.

Names with spaces need quotes: "Lt. Morales". Names with dots, apostrophes and hyphens don't: E.T.C., Kel'Thuzad. Since matching ignores punctuation, ETC and KelThuzad work too.

Statements

let NAME = PATTERN

Names a pattern so later statements can use it. The name must be defined before it is used; defining it again replaces it for the statements that follow. A let by itself produces no output.

find PATTERN

Runs the pattern against each replay and prints its matches. A query must contain at least one find, and can contain several. Each find has its own variable scope.

let myKill = death(victim: enemy, credit: me)
find myKill
find myKill count >= 3 within 12s

Events and fields

An event pattern is a kind with an optional filter list: death, death() and death(victim: me, credit: Tos) are all valid. Filters are ANDed and checked left to right (which matters only for variables). Using a field the kind doesn't have is a parse error that lists the valid fields.

Field types used below:

TypeWhat it holds
playerOne of the ten players. Matched by player name or hero name, or by me/ally/enemy.
player listSeveral players. A value matches the list if it matches any member.
teamTeam 0 or 1. Matched by me/ally (my team), enemy, 0/1 or team0/team1.
textA string, matched by name rules (case- and punctuation-insensitive, wildcards).
numberMatched by equality or >= <= > <.
boolMatched by true / false.

A field can be empty (no killing blow, no target point, unknown talent name). An empty field never matches, except under !.

A hero died. Time is exact (from the game loop).

killerplayerThe killing blow, when the replay records one. Shown with * in output. Can be empty even when credit isn't.

cast

A player issued an ability command: abilities, basic attacks, mount, hearthstone, talent actives, map-mechanic abilities. Plain move/right-click commands are not casts.

FieldTypeMeaning

A cast is the command, logged when the player confirms it. It doesn't mean the ability hit, or even fired: a cast that was interrupted or cancelled still appears.

A physical key went down or up. Only keys the game listens for are recorded (ability keys, digits, modifiers); each press appears twice, down then up.

FieldTypeMeaning

Keys are physical keys, not ability slots: a player who rebinds keys presses different keys for the same abilities. To ask about abilities, use cast with slot or abil.

Player lists

A value matches a player list (credit) when it matches any member. Negation applies to the whole list: credit: !me means “I'm not among the credited”, not “someone other than me is credited”.

Using me

me, ally and enemy need to know who “me” is. See --me under common options. If it's unknown, a query that uses them fails on that replay with an error.

Variables

A variable $name binds the field's value the first time it's used, and every later use must match that value. Bindings flow left to right through a pattern's filters and from each part of a sequence to the next.

# Someone killed me, and within a minute I took part in killing that same player
find death(victim: me, killer: $k) then death(victim: $k, credit: me) within 60s

# A hero died and respawned within 25 s (same player both times)
find death(victim: $p) then spawn(player: $p) within 25s
  • Lists: an unbound variable on a player list produces one candidate per member, so death(credit: $k) then chat(player: $k) within 5s finds whichever credited player chatted.
  • Equality: players compare as the same player; text compares case-insensitively; a player and a text value compare by name rules (player name or hero).
  • Scope: one find. A let pattern that uses a variable binds it wherever it's used.
  • Negative operators: the right side of not followed by and not preceded by can use bindings from the left side, but its own new bindings are dropped.
  • Order in preceded by: the left side (the later event) binds first, even though the right side happened earlier.
  • In near: the variable must already be bound, to a player or name.
  • Bindings are printed with each match: $k=Epicure (Deathwing).

Temporal operators

Every pattern produces matches. A match has a start time, an end time, the events that make it up, and its variable bindings. A single event's match starts and ends at the event's time. All windows below are inclusive, and within is required.

A then B within d

B starts no earlier than A ends and no later than A's end + d. B must be strictly after A, or at the same time but a different event. The result spans A's start to B's end.

  • Plain then: each A pairs with the earliest B in its window, and each B is used by at most one A, the earliest one that reaches it. Repeated A's leading to the same B therefore give one span, starting at the first A. (Deathwing re-aiming his flight three times, then dying, is one chase.)
  • then all: every (A, B) pair in the window.
find cast(player: me, slot: R) then death(victim: enemy, credit: me) within 4s
find cast(player: me, slot: R) then all death(victim: enemy, credit: me) within 4s

A not followed by B within d

Each A with no B in the window it would have under then. The match is A alone.

Game end: if A's end + d is past the end of the game, the replay can't tell whether B would have followed. These A's are left out and counted as undecided in the result line.

# I died and didn't ping within 10 s
find death(victim: me) not followed by ping(player: me) within 10s

A preceded by B within d

B starts between A's start − d and A's start, and ends no later than A's start (if at the same time, it's a different event). The closest such B is used; preceded by has no all form. The result spans B's start to A's end, with B's events first.

# A kill I took part in, with a ping from me in the 5 s before it
find death(victim: enemy, credit: me) preceded by ping(player: me) within 5s

A not preceded by B within d

Each A with no B in the window it would have under preceded by. The match is A alone. The start of the game doesn't make anything undecided; nothing happens before 0:00.

# My deaths with no enemy hero death in the 10 s before (not a trade)
find death(victim: me) not preceded by death(victim: enemy) within 10s

A count >= n within d

Groups A's matches by their variable bindings, then finds clusters of at least n matches whose start times all fit inside a span of d. Clusters are taken greedily from the earliest match: take every match starting within d of it; if there are at least n, that's a cluster, and the search continues after it. Otherwise it moves on one match. Clusters never overlap. The result spans the first match's start to the latest end, holds all the events, and is noted xN.

# 3+ enemy deaths credited to me within 12 s
find death(victim: enemy, credit: me) count >= 3 within 12s

# Any one enemy dying twice within 2 minutes, counted per victim
find death(victim: $v, credit: me) count >= 2 within 2m

n must be a whole number of at least 1. count works on any pattern, including sequences in parentheses.

Precedence and grouping

  • near and count bind tightest and apply to the pattern just before them. They can repeat: cast(...) near(me, 6) near(Tos, 6).
  • The four sequence operators have equal precedence and group left to right: A then B within 5s then C within 3s is (A then B within 5s) then C within 3s. C is timed from B's end.
  • Use parentheses for anything else: (A then B within 5s) count >= 2 within 1m, A then (B preceded by C within 2s) within 20s.

Proximity: near(subject, distance)

Applies to a single event pattern only. The event passes when it happened within distance map units of subject at that moment. Distances are in the same coordinates rq events prints.

Where the event happened: the event's own location if it has one (death position, cast target point or targeted unit, spawn point, unit death position). Otherwise, the acting player's hero position at that time.

Where the subject was: the subject's hero position at the event's time. If there are samples within 2 s on both sides, it's interpolated between them; otherwise the nearest sample within 2 s is used. With no sample within 2 s, the subject has no position and the event fails.

Subject is a value: me, ally, enemy, a player or hero name, a|b, or a bound variable. With several subject players, the event passes if any one is in range. With several near clauses, all must pass. Each passing clause adds a note: [2.5 from Player (estimated position)].

Positions are approximate. Replays only record a hero's position occasionally. Most samples are estimated from that player's move commands, so a hero who is stunned, channelling, standing still or being displaced can drift from the estimate or have gaps. Matches that rely on estimates are marked. Use generous distances (5–8) and check the result in the replay.

Ability labels

Replays identify an ability only by a numeric link id (abil), and record keys as physical keys, not slots. To label casts as Chromie.Q, rq builds a slot table per game build:

  1. It finds every replay on this machine from the same build.
  2. For each player in each replay, it pairs every cast with the key that player pressed just before it (within 3 s, with no other cast in between), and reads that key under default hotkeys: Q W E R D Z B, A = Attack, 1–5 = Active1–5.
  3. Each player casts one vote per ability id, for the slot they most often used. The slot with the most votes wins.

Because the label belongs to the ability id, not to anyone's keys, a player who rebinds keys is outvoted and their casts still get the right label.

LabelMeaning
Chromie.QAt least 60% of votes agree on the slot.
Deathwing.D?The top slot has under 60% of votes. Few votes, or the ability is reached in more than one way.
Deathwing.#1291No votes for this id (or --no-abil-table).
  • Shared abilities: mount, hearthstone, basic attack and map abilities (e.g. Dragon Knight) are one id for every hero, labelled with the caster's hero: Valla.Z, Valla.B.
  • Thin builds: a hero who appears in only a few replays of a build gets few votes. Check with rq abil-table --hero NAME, and fall back to abil: ids when slots look doubtful.
  • You are in every replay: your own bindings carry heavy weight for heroes you play.
  • Cache: the table is built the first time you query a build (progress on stderr), then cached in %LocalAppData%\MyHotsInfo\abil-slots\<build>.json. Rebuild after adding replays with rq abil-table --rebuild.

Ability names (abil-names.json)

To give ids real names, create %LocalAppData%\MyHotsInfo\abil-slots\abil-names.json, keyed by build and then id:

{
  "98348": {
    "1315": "Dragonflight",
    "1291": "Incinerate"
  }
}

Names appear in output as "Dragonflight" and can be matched with cast(name: Dragonflight). Ids can change between builds, so each build needs its own entries.

Errors

Parse errors give a line:column, the line, and a caret, and exit with code 2:

2:12: death has no field 'victm' (fields: victim, hero, credit, killer, x, y)
  find death(victm: me)
             ^
MessageCause
Unknown event or name 'X'Not an event kind, and no let by that name earlier in the query.
K has no field 'F'Misspelt or wrong field for that kind; the valid fields are listed.
Expected 'within'Every sequence operator and count needs a window.
Expected a duration like 10sThe window needs a unit: 10s, not 10.
'near' applies to a single event patternnear used after a sequence or a let name; put it on the event inside.
'X' is reservedA let name that's a keyword or event kind.
The query has no 'find' statementOnly lets.
…has no known 'me' (use --me)Runtime, per replay: me/ally/enemy with no identifiable “me”.
$x must be bound before it is used in near()Runtime: bind it in an earlier filter or event first.

Grammar

program   := statement+                                  # at least one find
statement := 'let' NAME '=' pattern
           | 'find' pattern

pattern   := postfix ( seqop postfix 'within' DURATION )*  # left-associative
seqop     := 'then' [ 'all' ]
           | 'not' 'followed' 'by'
           | 'preceded' 'by'
           | 'not' 'preceded' 'by'

postfix   := primary ( 'near' '(' value ',' NUMBER ')'      # event patterns only
                     | 'count' '>=' NUMBER 'within' DURATION )*
primary   := KIND [ '(' [ filter ( ',' filter )* ] ')' ]
           | NAME                                         # a let
           | '(' pattern ')'
filter    := FIELD ':' value

value     := unary ( '|' unary )*
unary     := '!' unary
           | ( '>=' | '<=' | '>' | '<' ) NUMBER
           | NUMBER | STRING | VARIABLE | 'me' | 'ally' | 'enemy' | NAME

KIND      := death | cast | key | chat | ping | talent | spawn | unitdied | levelup

Recipes

Fights and kills

# Enemy deaths I took part in
find death(victim: enemy, credit: me)

# Kills where I landed the killing blow
find death(victim: enemy, killer: me)

# Kills I got credit for without any ally credited (solo kills)
find death(victim: enemy, credit: me, credit: !ally)

# Team wipes: five enemy deaths inside 20 s
find death(victim: enemy) count >= 5 within 20s

# Revenge: killed by someone, then helped kill them within a minute
find death(victim: me, credit: $k) then death(victim: $k, credit: me) within 60s

My deaths

# Deaths to a specific hero
find death(victim: me, credit: Valeera)

# Dying within 5 s of using my heroic
find cast(player: me, slot: R) then death(victim: me) within 5s

# Deaths not traded: no enemy died in the 10 s before or after
find (death(victim: me) not preceded by death(victim: enemy) within 10s)
     not followed by death(victim: enemy) within 10s

# Dying soon after the enemy hit level 10
find levelup(team: enemy, level: 10) then death(victim: me) within 45s

Chases and positioning

# An enemy ability targeted right next to me, then that enemy died with my credit
find cast(player: enemy, player: $e) near(me, 5) then death(victim: $e, credit: me) within 30s

# My heroic aimed within 4 of any enemy hero
find cast(player: me, slot: R) near(enemy, 4)

Communication

# "gg" from anyone
find chat(text: "gg*")

# Chat from me right after a kill I was part of
find death(victim: enemy, credit: me) then chat(player: me) within 15s

# Ping spam: 5 pings from the same player inside 3 s
find ping(player: $p) count >= 5 within 3s

Builds and items

# My level-20 talent and when I took it
find talent(player: me, tier: 20)

# Any player picking a given talent (wildcards against the internal id)
find talent(name: "*SlowingSands")

# Hearthing right after a kill
find death(victim: enemy, credit: me) then cast(player: me, slot: B) within 8s

Limits of replay data

  • No damage, healing or health. Replays don't record hits, so “almost died” or “dealt the most damage in this fight” can't be asked.
  • Taunts, dances and other emotes don't appear in the replay data.
  • Casts are commands, not effects: a cast doesn't mean the ability hit, or even went off.
  • Positions are sparse and mostly estimated (see near).
  • Some times are whole seconds: chat, talent, spawn, unitdied and levelup. Deaths, casts, keys and pings are exact to 1/16 s.
  • Ability ids are per build; labels depend on how many replays of that build you have.
